# Feature Specification: build-recipe-plugin → build-logic Convention Plugin 전환

**Feature Branch**: `chore/build-logic-migration`

**Created**: 2026-09-08

**Status**: Draft

**Input**: Gradle 빌드 시스템을 LINE `com.linecorp.build-recipe-plugin`(라벨 기반 `configureByLabel`)에서 `build-logic` composite build 기반 convention plugin 체계로 마이그레이션한다. 동작 무변경(behavior-preserving) 교체이며, 수용 기준은 마이그레이션 전/후 의존성 그래프의 완전 동일성이다.

## User Scenarios & Testing *(mandatory)*

이 기능의 사용자는 **최종 사용자가 아니라 이 저장소의 빌드 이해관계자**다: 기여 개발자, CI 파이프라인, pre-commit 훅, 의존성 봇.

### User Story 1 - 모듈 스크립트만 보고 빌드 설정을 파악한다 (Priority: P1)

기여자가 어떤 모듈의 빌드 설정을 이해하려 할 때, 그 모듈의 빌드 스크립트 한 파일만 열어서 이 모듈이 어떤 설정 묶음을 받는지 알 수 있어야 한다. 현재는 모듈 옆 속성 파일에 적힌 라벨 문자열을 읽고, 루트 빌드 스크립트로 건너가 그 라벨에 걸린 블록을 찾아야 한다 — IDE의 정의 이동도, 자동완성도, 타입 검사도 걸리지 않는 문자열 간접참조다.

**Why this priority**: 이 마이그레이션이 존재하는 이유 자체다. 나머지 스토리는 이 변경을 안전하게 만들기 위한 것이다.

**Independent Test**: 6개 모듈 각각의 빌드 스크립트를 열어, 다른 파일을 참조하지 않고도 적용되는 설정 묶음의 이름을 읽어낼 수 있는지 확인한다. 모듈 옆 라벨 속성 파일이 저장소에 하나도 남지 않았는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기여자가 임의의 모듈 빌드 스크립트를 열었을 때, **When** 파일 상단의 플러그인 선언 블록을 읽으면, **Then** 그 모듈에 적용되는 설정 묶음의 이름이 명시적으로 보이고 IDE에서 해당 정의로 이동할 수 있다.
2. **Given** 마이그레이션이 완료된 저장소에서, **When** 모듈 디렉터리에서 라벨 선언 속성 파일을 찾으면, **Then** 하나도 존재하지 않는다.
3. **Given** 설정 묶음 정의 파일에서, **When** 버전 카탈로그의 항목을 참조하면, **Then** 문자열이 아닌 타입 검사되는 참조로 해석되고 오타 시 컴파일 단계에서 실패한다.

---

### User Story 2 - 전환이 런타임 동작을 바꾸지 않았음을 증명한다 (Priority: P1)

리뷰어가 이 변경을 승인하려면 "빌드가 통과한다"보다 강한 증거가 필요하다. 설정 이관 과정에서 의존성이 하나 빠지거나 추가되면 컴파일은 통과하고 런타임에 터진다. 전환 전후의 의존성 그래프가 완전히 동일함을 기계적으로 보여야 한다.

**Why this priority**: 무행위변경이 이 작업의 계약이다. 증명 없이는 계약이 성립하지 않는다.

**Independent Test**: 전환 전 상태와 전환 후 상태에서 각 모듈의 의존성 보고서를 생성해 텍스트 비교한다. 차이가 없으면 통과.

**Acceptance Scenarios**:

1. **Given** 전환 전 시점에 캡처한 6개 모듈의 의존성 보고서가 있을 때, **When** 전환 후 동일한 보고서를 다시 생성해 비교하면, **Then** 일곱 개 축(컴파일, 런타임, 테스트컴파일, 테스트런타임, 애너테이션 프로세서, 테스트 애너테이션 프로세서, 정적 분석) 모두에서 차이가 0건이다.
2. **Given** 전환된 저장소에서, **When** 전체 빌드를 실행하면, **Then** 성공하고 배포용 실행 아카이브가 이전과 동일한 이름으로 산출된다.
3. **Given** 전환된 저장소에서, **When** 컨테이너 이미지 산출 작업을 실행하면, **Then** 정상적으로 산출물이 생성된다.
4. **Given** 실행 아카이브가 필요 없는 모듈에서, **When** 실행 아카이브 생성 작업을 호출하면, **Then** 이전과 동일하게 건너뛰어지고 산출물이 생기지 않는다.

---

### User Story 3 - 기존 빌드 명령어가 그대로 동작한다 (Priority: P2)

CI 파이프라인, pre-commit/pre-push 훅, 개발자의 손에 익은 명령어가 이 전환 때문에 바뀌어서는 안 된다. 빌드 체계를 갈아끼우면서 팀의 근육 기억과 파이프라인 정의까지 함께 고치면 회귀 원인이 섞인다.

**Why this priority**: 전환의 파급 범위를 빌드 정의 안으로 가둔다. P1은 아니지만 어겨지면 전환 비용이 크게 는다.

**Independent Test**: CI 워크플로우 파일과 훅 설정 파일의 변경 여부를 확인하고, 거기 적힌 명령어를 그대로 실행해 성공하는지 본다.

**Acceptance Scenarios**:

1. **Given** 전환된 저장소에서, **When** CI 워크플로우 정의와 pre-commit/pre-push 훅 정의의 명령어를 확인하면, **Then** 전환 전과 동일하다.
2. **Given** 전환된 저장소에서, **When** CI의 5개 게이트를 모두 실행하면, **Then** 전부 통과한다.
3. **Given** 기여자가 포맷 검사·정적 분석·단위 테스트 명령을 실행하면, **Then** 전환 전과 같은 이름의 작업이 같은 범위를 검사한다.

---

### User Story 4 - 빌드 정의의 의존성도 자동 업데이트 대상이 된다 (Priority: P3)

빌드 정의가 별도 빌드로 분리되면 그 안의 버전은 기본 설정으로는 의존성 봇의 시야 밖에 놓인다. 방치하면 본체는 갱신되는데 빌드 정의만 낡아 조용히 어긋난다.

**Why this priority**: 즉시 깨지지 않지만 시간이 지나며 확실히 부패하는 종류의 부채다. 전환과 같은 변경에서 함께 막는 것이 가장 싸다.

**Independent Test**: 의존성 봇 설정이 빌드 정의 디렉터리를 스캔 대상에 포함하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 전환된 저장소에서, **When** 의존성 봇 설정을 확인하면, **Then** 루트와 빌드 정의 디렉터리가 모두 스캔 대상으로 선언되어 있다.

---

### Edge Cases

- **빌드 정의를 컴파일한 JVM보다 낮은 JVM에서 빌드를 실행하면?** 설정 묶음은 컴파일 시점 JVM에 맞춰 산출되며, 더 낮은 JVM에서는 로드 자체가 실패한다. 실패 메시지가 원인을 설명하지 않으므로, 산출 대상 JVM을 명시적으로 고정해 이 조합이 우연히 성립하지 않도록 한다.
- **빌드 정의만 따로 빌드하려 하면?** 빌드 정의는 최상위 빌드에서 구동되어야만 성립한다. 단독 구동은 실패한다 — CI나 스크립트에 그런 호출을 넣지 않는다.
- **프로젝트 격리(Isolated Projects) 최적화를 켜면?** 선택한 빌드 정의 구조는 이 최적화와 호환되지 않는다. 켜지 않으며, 이 제약을 결정 기록에 남긴다.
- **실행 아카이브가 필요 없는 모듈에 아카이브 작업이 생기면?** 공통 설정 묶음이 기본적으로 비활성화하고, 필요한 모듈만 별도 묶음으로 되켠다.
- **포맷 검사 도구가 모듈별로 각자 로드되면?** 공유 서비스가 모듈마다 다른 클래스로더로 중복 로드되어 실패한다. 최상위 빌드에서 한 번 등록해 공통 상위 스코프를 공유시킨다.
- **새 모듈을 추가하면?** 기여자는 새 모듈 스크립트에 필요한 설정 묶음을 명시적으로 선언해야 한다. 선언을 빠뜨리면 설정이 조용히 누락되는 것이 아니라 컴파일 또는 의존성 해석 단계에서 드러난다.

## Requirements *(mandatory)*

### Functional Requirements

**구조**

- **FR-001**: 빌드 설정은 루트 빌드 스크립트의 라벨 조건 블록이 아니라, 별도 빌드로 분리된 재사용 가능한 설정 묶음으로 정의되어야 한다.
- **FR-002**: 설정 묶음은 현행 라벨 4종과 1:1로 대응하는 4개여야 한다 — 공통 자바, 스프링, 테스트, 실행 아카이브.
- **FR-003**: 각 모듈은 자기 빌드 스크립트에서 필요한 설정 묶음을 명시적으로 선언해 적용해야 한다.
- **FR-004**: 모듈별 라벨 선언 속성 파일 6개는 저장소에서 완전히 제거되어야 한다.
- **FR-005**: 설정 묶음 정의는 프로젝트의 단일 버전 목록을 타입 검사되는 방식으로 참조해야 한다 — 버전 문자열이 두 곳에 복제되어서는 안 된다.

**동작 보존**

- **FR-006**: 전환 후 6개 모듈 각각의 의존성 그래프는 SC-001이 정의하는 일곱 개 축 전부에서 전환 전과 완전히 동일해야 한다.
- **FR-007**: 프로젝트 좌표(그룹, 버전)는 최상위 빌드에 남아 릴리스 시 한 곳에서 수정 가능해야 한다.
- **FR-008**: 실행 아카이브는 전환 전과 동일하게 배포 대상 모듈에서만 생성되고 나머지 모듈에서는 생성되지 않아야 한다.
- **FR-009**: 컨테이너 이미지 산출 설정은 배포 대상 모듈에만 적용되어야 한다.
- **FR-010**: 특정 모듈에만 걸려 있고 라벨 체계 밖에서 선언된 코드 생성·변이 테스트 설정은 이번 전환에서 변경하지 않는다.
- **FR-011**: 저장소 선언은 최상위 빌드 한 곳으로 통합하되, 해석되는 저장소 집합은 전환 전과 동일해야 한다.

**검증 및 도구 연동**

- **FR-012**: 포맷 검사는 모듈 단위 작업으로 분할되어 모듈별 선택 실행이 가능해야 하며, 검사 대상 소스 집합은 전환 전과 동일해야 한다.
- **FR-013**: CI 워크플로우와 커밋 훅에 적힌 명령어는 변경되지 않아야 한다.
- **FR-014**: 설정 묶음의 산출 대상 JVM 버전은 빌드 실행 JVM에 암묵적으로 따라가지 않고 명시적으로 고정되어야 한다.
- **FR-015**: 의존성 봇 설정은 루트와 빌드 정의 디렉터리를 모두 스캔 대상으로 선언해야 한다.

**기록**

- **FR-016**: 이 전환의 배경, 채택한 구조, 수용한 제약을 결정 기록으로 남기고 결정 기록 인덱스를 갱신해야 한다.
- **FR-017**: 전환 과정에서 발견된 기존 설정의 하자는 이번 변경에서 수정하지 않고 후속 작업으로 분리 기록해야 한다.

### Key Entities

- **설정 묶음(Convention)**: 여러 모듈이 공유하는 빌드 설정의 재사용 단위. 이름으로 식별되며 모듈이 명시적으로 선언해 적용한다. 현행 라벨 하나에 대응한다.
- **모듈**: 빌드의 최소 단위. 자신이 적용할 설정 묶음의 집합과, 자신에게만 해당하는 고유 설정을 선언한다.
- **버전 목록**: 프로젝트가 사용하는 모든 외부 구성요소의 버전을 모아 둔 단일 출처. 본체 빌드와 빌드 정의가 함께 참조한다.
- **의존성 기준선(Baseline)**: 전환 전 시점에 캡처한 모듈별 의존성 보고서. 전환 후 비교 대상이며 저장소에 커밋하지 않는 일회성 검증 자료다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 6개 모듈 × 7개 의존성 축, 총 **42건**의 의존성 보고서 비교에서 차이가 **0건**이다. 일곱 축은 컴파일·런타임·테스트컴파일·테스트런타임·애너테이션 프로세서·테스트 애너테이션 프로세서·정적 분석이다. 정적 분석과 애너테이션 프로세서 축이 없으면 그 축에만 붙는 구성요소의 누락을 컴파일·런타임 비교로는 잡을 수 없다.
- **SC-002**: CI의 5개 게이트가 **전부 통과**한다.
- **SC-003**: 전체 빌드와 컨테이너 이미지 산출이 모두 성공한다.
- **SC-004**: CI 워크플로우 정의와 커밋 훅 정의에서 **명령어 변경이 0건**이다.
- **SC-005**: 저장소에 남은 라벨 선언 속성 파일이 **0개**다.
- **SC-006**: 6개 모듈 **전부**가 자기 빌드 스크립트 안에서 적용 설정 묶음을 명시 선언하며(6/6), 다른 파일을 읽어야만 알 수 있는 암묵적 적용 경로가 **0건**이다. 전환 전에는 파악에 3개 파일이 필요했다(모듈 속성 파일 → 루트 스크립트 → 해당 라벨 블록).
- **SC-007**: 버전 목록에 이미 존재하는 구성요소의 버전 문자열이 빌드 정의에 리터럴로 재선언된 항목이 **0건**이다. 유일한 예외는 버전 목록을 등록하는 주체 자신의 버전이며(자기 참조 순환 때문에 리터럴이 불가피하다), 이 예외는 1건을 넘지 않는다.
- **SC-008**: 전환 과정에서 발견된 기존 하자가 **하나도 이번 변경에 섞이지 않고** 전부 후속 작업으로 분리 기록된다.
- **SC-009**: 이 전환의 결정 기록 **1건**이 작성되고 결정 기록 인덱스에 반영된다.
- **SC-010**: 빌드 정의에서 산출 대상 JVM이 명시적으로 선언된 지점이 **1곳** 존재하며, 빌드 실행 JVM에 암묵적으로 위임하는 지점이 **0곳**이다.

## Assumptions

**검증된 전제** — 아래는 추측이 아니라 이 저장소의 빌드 도구 조합으로 실제 시험해 확인한 사실이다.

- 선택한 빌드 정의 방식은 현재 사용 중인 빌드 도구 버전과 실행 JVM 조합에서 동작한다.
- 설정 묶음 안에서 확장 설정 블록에 접근하려면, 그 블록을 제공하는 플러그인이 **해당 설정 묶음 자신의 선언부**에 있어야 한다. 다른 설정 묶음이 같은 플러그인을 적용하더라도 접근자는 생성되지 않는다. 중복 선언은 무해하다.
- 스프링 설정 묶음은 스프링 빌드 플러그인을 반드시 적용해야 한다 — 버전을 생략한 스프링 구성요소들이 이 플러그인이 공급하는 버전 목록에 의존한다.
- 실행 아카이브를 공통 묶음에서 비활성화하고 전용 묶음에서 되켜는 방식이 의도대로 동작한다.
- 설정 묶음의 산출 대상 JVM은 빌드 실행 JVM을 따라간다. 경고 없이 따라가므로 명시적 고정이 필요하다.
- 선택한 빌드 정의 구조는 프로젝트 격리 최적화와 호환되지 않는다.

**수용한 제약**

- 프로젝트 격리 최적화는 사용하지 않는다. 이 제약은 결정 기록에 남기며, 향후 빌드 성능 작업 시 빌드 정의 구조를 재검토한다.
- 설정 묶음의 산출 대상 JVM은 현재 프로젝트 표준 JVM으로 고정한다. 팀에 그보다 낮은 JVM으로 빌드하는 환경이 생기면 이 값을 그 하한으로 내린다.
- 빌드 정의는 최상위 빌드를 통해서만 구동한다. 단독 구동 명령을 스크립트나 CI에 넣지 않는다.

**범위 경계**

- 빌드 구성 캐시 도입은 이번 범위 밖이다. 후속 작업으로 기록한다.
- 전환 과정에서 드러난 기존 설정의 하자(실효 없는 커버리지 규칙, 대상 패키지가 잘못 지정되어 자사 코드를 검사하지 않는 정적 분석 설정, 테스트 의존성 중복 선언)는 수정하지 않는다. 지금 고치면 무행위변경 계약이 깨지고 회귀 원인이 섞인다.
- 애플리케이션 소스 코드는 한 줄도 변경하지 않는다.
- 전환은 단일 변경으로 수행한다. 두 체계가 공존하는 중간 상태를 만들지 않는다.

**작업 환경 전제**

- 작업은 격리된 작업 공간에서 수행하며, 전환 전 상태를 그대로 유지하는 기준선 확보 경로가 필요하다.
- 의존성 기준선은 저장소 밖에 보관하고 커밋하지 않는다 — 저장소에 두면 의존성 갱신마다 함께 고쳐야 하는 부채가 된다.
